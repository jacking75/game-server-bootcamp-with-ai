# Phase 5. 운영 품질: 성능·관측·배포·보안 (16~20주, 200h)

> 공통 140h / 트랙 60h. 이 Phase가 끝나면 학습자는 만든 서버를 **측정 → 가설 → 수정 → 재측정**으로 개선하고, Windows 서비스로 배포하고, 장애를 재현·대응해 "운영 가능한 서버"로 만든다.

## 1. 개요

### 1.1 목표
- 시나리오 기반 더미 클라이언트로 부하를 재현하고 TPS·p99·에러율을 측정한다
- 프로파일러로 병목을 찾고 최소 2개를 수치로 개선한다
- Prometheus/Grafana로 서버 지표를 관측하고 알람을 설정한다
- Windows 서비스로 배포하고 GitHub Actions로 빌드·테스트·배포를 자동화한다(Docker 미사용)
- 장애 주입(DB 다운·Redis 지연·네트워크 단절)에서 서버가 살아남고 복구되게 만든다
- 레이트 리밋·입력 검증·시크릿 관리 등 기본 보안을 적용한다

### 1.2 선수 조건
- Phase 3·4 완료(게임 서버 + API 서버 연동 상태), 배포 대상 머신 준비

### 1.3 이 Phase가 끝나면 할 수 있는 것
- "p99가 왜 튀는가"를 프로파일러 결과로 설명한다
- 대시보드의 지표 하나하나를 왜 넣었는지 말한다
- `git push` 한 번으로 테스트·배포가 돌아가는 파이프라인을 갖는다
- 장애 발생 시 런북대로 5분 내 원인 후보를 좁힌다

## 3. 학습 항목 상세

### 3.1 공통 (140h)

**부하 테스트 설계 (16h)**
- 무엇: 시나리오(접속 → 로그인 → 매칭 → 플레이 → 결과 → 반복), 램프업(N명/초), 정상 상태 유지 시간, 지표(TPS, p50/p95/p99, 에러율, 접속 수), 클라이언트 병목 분리(클라이언트 CPU·포트 고갈), 결과 재현성(3회 실행 편차), API 부하는 k6 또는 NBomber도 가능하나 이 과정은 자작 툴 우선
- 왜: 측정이 신뢰되지 않으면 개선도 신뢰되지 않는다
- 확인: 같은 조건 3회 실행 결과의 p99 편차 10% 이내

**관측: 메트릭·로그·알람 (24h)**
- 무엇: 메트릭 종류(카운터·게이지·히스토그램), RED(요청·에러·지연)/USE(사용률·포화·에러), 라벨 설계와 카디널리티 폭발 주의, Prometheus 스크레이프·PromQL 기초, Grafana 패널·변수, 알람 규칙(조건·지속 시간), 구조화 로그 수집(파일 → fluent-package 선택), 로그와 메트릭의 역할 분담, 분산 추적(OpenTelemetry) 개념
- 왜: 운영 중 "지금 무슨 일이 일어나는가"를 5초 안에 알아야 한다
- 확인: 대시보드에서 부하 시작·종료 시점이 그래프로 보이고 알람이 실제 발동한 로그

**성능 분석 방법론 (20h)**
- 무엇: 병목 가설 수립(CPU·메모리·락·I/O·네트워크·DB), 관찰 → 가설 → 실험 → 기각/채택 루프, 핫패스 식별(프로파일러 상위 함수), 할당 프로파일, 락 경합 프로파일, "측정 없이 최적화 금지", 개선 리포트 구조(전/후 수치·변경점·부작용)
- 왜: 5-2의 핵심이자 면접에서 가장 설득력 있는 이야기
- 확인: 기각된 가설이 리포트에 최소 1개 기록

**Windows 배포 (20h)**
- 무엇: Windows 서비스 개념(SCM, 시작 유형, 복구 옵션), 서비스 계정·권한, 설치 경로·설정 파일·로그 경로 분리, 환경별 설정(Dev/Stage/Prod), 시크릿(환경 변수·DPAPI·별도 파일 권한), 방화벽 규칙, 배포 스크립트(PowerShell: 중지 → 파일 교체 → 시작 → 헬스 체크), 롤백, 무중단 배포 개념(포트 교체·로드밸런서), 원격 배포(WinRM/PowerShell Remoting 또는 SSH)
- 왜: Docker 없이 Windows에서 서비스를 올리는 것이 국내 다수 게임 서버 운영의 현실이다
- 확인: 배포 스크립트 1회 실행으로 새 버전이 서비스로 기동되고 헬스 체크 통과, 실패 시 롤백

**CI/CD (12h)**
- 무엇: GitHub Actions `windows-latest` 워크플로(빌드·테스트·아티팩트), 태그 기반 릴리스, 배포 잡(self-hosted runner를 배포 머신에 설치하거나 SSH/WinRM으로 원격 실행), 시크릿 저장소, 정적 분석 단계
- 확인: `git push` → 테스트 → 아티팩트 → 배포 머신 반영까지 자동

**장애 대응 (24h)**
- 무엇: 장애 주입(MySQL 서비스 중지, Redis 지연/중지, 게임↔API 간 네트워크 차단(방화벽 규칙), 디스크 풀, CPU 점유), 실패 모드 설계(빠른 실패 vs 대기), 재시도·지수 백오프·지터, 서킷 브레이커, 타임아웃 계층, 백프레셔(큐 상한·접속 제한), 부분 기능 저하(degradation), 런북(감지·진단·대응·복구·사후), 사후 분석(포스트모템)
- 왜: "죽지 않는 서버"보다 "죽어도 예측대로 죽고 스스로 복구하는 서버"가 목표
- 확인: 5-4 장애 3종에서 크래시 0, 복구 시간 기록

**보안 기초 (12h)**
- 무엇: 레이트 리밋(토큰 버킷, 접속당/IP당), 입력 검증(길이·범위·상태), 플러딩 방어(접속 수 제한·패킷 크기·미인증 세션 타임아웃), TLS/DTLS 개념과 게임 서버에서의 적용 범위(API는 TLS, 소켓은 선택), 시크릿 노출 방지(로그·저장소), 의존성 취약점 점검
- 확인: 초당 1,000 접속 시도 플러딩에서 정상 유저 지연 영향 최소, 레이트 리밋 테스트

**크래시 분석 (12h)**
- 무엇: 크래시 덤프 자동 수집(Windows Error Reporting LocalDumps 레지스트리, procdump), 덤프 열기(WinDbg / VS), 스택·스레드·힙 확인, 심볼 관리(PDB 보관)
- 확인: 5-5 심화 또는 최소한 덤프 1개를 열어 크래시 라인 특정

### 5.1 프롬프트

병목 가설
```
부하 테스트 결과다: 300접속·100룸에서 착수 p99 120ms(목표 50ms), CPU 35%, GC(또는 컨텍스트 스위칭) 지표는 (첨부), 대시보드 스크린샷 (첨부).
병목 가설을 3개 이상 세우고, 각 가설을 확인할 관찰 방법(프로파일러 뷰·카운터·로그)을 제시해 달라.
나는 각 가설을 실험으로 확인한 뒤 결과를 가져오겠다. 결론을 먼저 내리지 말라.
```

프로파일러 결과 해석(내 해석 먼저)
```
프로파일러 상위 함수 표: (붙여넣기)
내 해석: "(3문장)"
내 해석에서 틀린 점, 그리고 이 표만으로는 알 수 없는 것(측정 오버헤드·샘플링 한계)을 지적해 달라.
```

장애 시나리오 생성
```
내 서버 구성(게임 서버 + API 서버 + MySQL + Redis, 모두 Windows)에서 실제로 일어날 법한 장애 시나리오를 무작위로 하나 제시해 달라. 조건: 재현 가능해야 하고, 재현 방법(서비스 중지·방화벽 규칙·지연 주입 등)을 함께 줄 것.
나는 대응 후 런북을 가져오겠다. 런북을 "새벽 3시에 처음 보는 운영자" 관점으로 리뷰해 달라.
```

Dockerfile 대신 배포 스크립트
```
Windows 서비스로 배포하는 PowerShell 스크립트 초안을 작성해 달라: 서비스 중지 → 백업 → 파일 교체 → 설정 파일 유지 → 서비스 시작 → 헬스 체크 → 실패 시 롤백.
각 줄에 왜 필요한지 주석을 달아라. 나는 주석을 내 말로 다시 쓰고 실행 결과를 검토하겠다.
```

### 5.2 맡길 것 / 맡기지 않을 것
| 맡긴다 | 맡기지 않는다 |
|---|---|
| CI 워크플로·배포 스크립트 초안 | 병목 판정과 최적화 우선순위 |

### 5.3 AI가 자주 틀리는 지점
- 측정 없이 "이 코드는 느리니 이렇게 바꿔라" 제안 → 반드시 전/후 수치 요구
- 히스토그램 버킷을 기본값으로 두어 p99가 무의미해짐 → 버킷 경계를 목표치(50ms) 주변으로 설계
- 재시도를 무한/즉시로 제안 → 상한·백오프·지터
- 서킷 브레이커를 열어 두고 복구 조건(half-open)을 빠뜨림
- Windows 서비스에서 콘솔 출력·현재 디렉터리 가정으로 인한 실패를 예상 못 함

## 6. 과제 명세

### 6.1 공통 과제 5-C. 관측 스택 구축 (필수, 24h)

요구사항
1. Prometheus·Grafana·windows_exporter를 Windows에 설치(개발 PC와 배포 머신 각각)
2. 게임 서버(3-1) 메트릭: 접속 수(게이지), 룸 수, 패킷 수신/송신(카운터, 패킷ID 라벨은 상위 20개만), 착수 처리 지연(히스토그램, 버킷 1/5/10/25/50/100/250/500ms), 송신 큐 길이 최대값, 세션 종료 사유별 카운터, 풀 미반환 수
3. API 서버(4-1) 메트릭: 엔드포인트별 요청 수·에러 수·지연 히스토그램, DB 쿼리 지연, Redis 명령 지연, 연결 풀 사용률
4. 시스템: windows_exporter CPU·메모리·네트워크·디스크
5. 대시보드 1개(행: 개요 / 게임 서버 / API 서버 / DB·Redis / 시스템), 변수로 인스턴스 선택
6. 알람 2개 이상: 착수 p99 > 100ms 1분 지속, 에러율 > 1% 1분 지속. 발동 시 로그 또는 Windows 알림
7. 구조화 로그를 파일로 남기고(일 단위 롤링), 필요 시 fluent-package로 MySQL 저장(선택)

제출물: 대시보드 JSON, 알람 규칙, 부하 중 스크린샷, 알람 발동 로그

채점: 메트릭 설계(카디널리티·버킷 근거) 40 / 대시보드 유용성 30 / 알람 동작 30

## 8. 흔한 막힘 포인트

| 증상 | 원인 | 대처 |
|---|---|---|
| 서비스가 시작 직후 종료 | 작업 디렉터리가 System32, 설정 파일 상대 경로 | 실행 파일 경로 기준으로 설정 경로 계산, 이벤트 로그 확인 |
| Prometheus가 타깃을 못 긁음 | 방화벽, 바인딩 주소 localhost | 메트릭 포트 인바운드 허용(내부만), `0.0.0.0` 또는 내부 IP 바인딩 |
| 프로파일러 결과가 부하 없이 찍힘 | 수집 시점 오류 | 부하 정상 상태 진입 후 30초간 수집 |
| self-hosted runner가 서비스 제어 권한 없음 | runner 계정 권한 | runner를 관리자 계정 서비스로, 또는 배포 스크립트만 승격 |
| 재시도가 장애를 악화 | 즉시 재시도 폭주 | 백오프·지터·상한, 서킷 브레이커 |
| 장애 후 서킷이 안 닫힘 | half-open 로직 누락 | 일정 시간 후 시험 요청 1개 허용 |
| 더미 클라이언트가 먼저 죽음 | 클라이언트 포트/CPU 한계 | 2대 분산, 동적 포트 범위 확대 |
