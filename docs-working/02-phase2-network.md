# Phase 2. 네트워크 프로그래밍 기초 (4~7주, 160h)

> 공통 70h / 트랙 90h. 이 Phase가 끝나면 학습자는 소켓 수준에서 TCP를 다루고, 패킷 프로토콜을 스스로 설계·구현하며, 수백 접속을 Windows에서 안정적으로 유지하는 서버를 만든다.

## 1. 개요

### 1.1 목표
- TCP의 스트림 특성(경계 없음), 연결 수립·종료, 흐름·혼잡 제어를 **Wireshark로 눈으로 확인**하고 설명한다
- 길이 헤더 기반 패킷 프레이밍과 직렬화를 직접 구현하고, 분할·병합·손상 입력을 방어한다
- C#: `Socket` + `SocketAsyncEventArgs`(또는 Pipelines) 기반 비동기 서버를 만든다
- C++: Winsock → select → Overlapped I/O → IOCP 순으로 Windows 비동기 I/O 모델을 익히고 IOCP 서버를 만든다
- 500 동시 접속에서 10분간 유실·크래시 없는 채팅 서버를 만든다

### 1.2 선수 조건
- Phase 1 완료(특히 스레드 세이프 큐, 오브젝트 풀, 디버거 사용)

### 1.3 이 Phase가 끝나면 할 수 있는 것
- 에코 서버를 30분 안에 빈 프로젝트에서 작성한다
- "패킷이 잘려서 온다"는 현상을 재현하고 프레이밍 파서로 해결한다
- 세션 종료 시점의 경쟁 조건(수신 중 종료, 송신 중 종료)을 설명하고 방어한다
- 500 접속 부하 테스트를 직접 만든 클라이언트로 수행하고 결과를 표로 낸다

## 3. 학습 항목 상세

### 3.1 공통 (70h)

**네트워크 기초 이론 (12h)**
- 무엇: OSI/TCP-IP 계층, 캡슐화, IP·포트·NAT, MTU/MSS, ARP/ICMP 개요
- 왜: 이후 "왜 패킷이 잘리는가", "왜 로컬에서 되던 게 외부에서 안 되는가"를 계층으로 설명하기 위해
- 확인: 자기 서버로 가는 패킷의 계층별 헤더를 Wireshark에서 펼쳐 각 필드의 의미를 노트에 적는다

**TCP 동작 (14h)**
- 무엇: 3-way handshake, 4-way 종료, TIME_WAIT/CLOSE_WAIT, 시퀀스/ACK, 흐름 제어(윈도우), 혼잡 제어 개념, Nagle과 지연 ACK, keep-alive, RST
- 왜: 게임 서버의 "접속 끊김 감지", "지연 원인", "포트 고갈"이 전부 여기서 나온다
- 확인: (1) 핸드셰이크 캡처, (2) 서버가 먼저 닫을 때와 클라이언트가 먼저 닫을 때 `netstat`/`Get-NetTCPConnection`의 상태 차이 표, (3) Nagle 켜고 끈 상태의 작은 패킷 100개 전송 캡처 비교

**스트림 특성과 프레이밍 (12h)**
- 무엇: TCP는 메시지 경계가 없다. 길이 접두 프레이밍, 구분자 프레이밍, 헤더(길이·ID·버전·플래그) 설계, 최대 패킷 크기 제한, 링 버퍼, 엔디안(네트워크 바이트 오더)
- 왜: 프레이밍이 잘못되면 서버가 임의 시점에 죽거나 메모리를 폭발시킨다
- 확인: 64KB 패킷을 보내 수신이 여러 번에 나뉘는 로그, 두 패킷이 붙어 오는 로그를 각각 캡처

**직렬화 (8h)**
- 무엇: 바이너리 수동 직렬화(BinaryPrimitives / memcpy), MemoryPack, MessagePack, Protobuf, FlatBuffers의 크기·속도·스키마 진화·언어 지원 비교
- 왜: 프로토콜은 클라이언트와 공유되므로 선택 근거를 설명할 수 있어야 한다
- 확인: 같은 패킷 5종을 2가지 방식으로 직렬화해 바이트 크기와 처리 시간 표를 만든다

**세션 관리 (10h)**
- 무엇: 세션 상태 머신(접속→인증 전→인증 후→종료 중→종료), 타임아웃, 하트비트, 중복 접속, 강제 종료, 종료 중 수신/송신 경쟁, 재접속
- 왜: Phase 3 게임 서버의 유저 관리가 이 위에 올라간다
- 확인: "종료 중인 세션에 송신이 들어오면 어떻게 되는가"를 코드 경로로 설명하고 테스트로 재현

**서버 I/O 모델 개론 (6h)**
- 무엇: 스레드-퍼-커넥션 → select → 비동기 완료 모델(IOCP) → epoll/io_uring(개념), C10K 문제, 완료 통지 vs 준비 통지
- 왜: 자기 트랙의 API가 어느 모델인지 알고 다른 모델과 비교할 수 있어야 면접에서 설명이 된다
- 확인: 4가지 모델을 "접속 1만 개일 때 스레드 수·시스템 콜 수·메모리" 관점으로 비교표 작성

**부하 테스트 기초 (8h)**
- 무엇: 램프업, 동시 접속 vs 초당 접속, 메시지율, 성공/실패/지연 통계(p50/p99), 로컬 루프백 테스트의 한계(포트 고갈, 클라이언트 병목)
- 왜: 2-1의 "500 접속·10분" 조건을 스스로 증명해야 한다
- 확인: 2-3 클라이언트 실행 결과 표

### 6.3 트랙 과제 2-2. 패킷 프레이밍·직렬화 라이브러리 (필수, 24h)

목표: 2-C 명세를 라이브러리로 구현해 2-1과 이후 Phase에서 재사용한다.

### 7.3 설명 시험 예시 질문
공통
- 3-way handshake의 각 단계에서 서버 소켓 상태는 무엇인가. SYN 플러딩은 어느 단계를 공격하는가
- TIME_WAIT은 누가, 왜 가지는가. 서버가 먼저 끊으면 어떤 문제가 생기는가
- TCP에서 메시지 경계가 없다는 것을 코드에서 어떻게 다루는가. 길이 접두 방식의 취약점은
- Nagle을 끄는 이유와 끄지 말아야 하는 경우
- IOCP(완료 통지)와 epoll(준비 통지)의 차이를 recv 흐름으로 설명하라

C#
- SAEA를 재사용하는 이유. `ReceiveAsync`가 false를 반환하면 무엇을 해야 하는가
- 세션별 송신 큐가 필요한 이유와, 큐가 무한히 커지는 것을 막는 방법
- `ArrayPool`을 소켓 버퍼에 쓸 때 주의점(반환 시점, 고정)

C++
- IOCP 워커 스레드 수를 어떻게 정하는가. 코어 수보다 많이 두면 어떤 일이 생기는가
