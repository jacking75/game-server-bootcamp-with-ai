# Phase 4. 데이터·API 서버 (12~15주, 160h)

> 공통 100h / 트랙 60h. 이 Phase가 끝나면 학습자는 계정·자산 데이터를 다루는 HTTP API 서버와 DB를 실무 구조로 만들고, 동시성 문제(재화 복제 등)를 트랜잭션으로 방어한다.

## 1. 개요

### 1.1 목표
- 게임 API 서버 흐름(버전 체크 → 로그인 → 데이터 로드 → 로비 행동)을 설계하고 구현한다
- MySQL 스키마·인덱스·트랜잭션·격리 수준을 실제 데이터 100만 건으로 검증한다
- Redis를 세션·랭킹·캐시·분산 락 용도로 구분해 쓴다
- 이중 지출·중복 요청·토큰 탈취 같은 악용 시나리오를 도출하고 테스트로 방어를 증명한다
- Phase 3 게임 서버와 API 서버를 서버 간 인증으로 연동한다

### 1.2 트랙 경로 (이 Phase만 특례)
- **C# 트랙**: ASP.NET Core Web API
- **C++ 트랙**: 다음 중 택1
  - (a) 순수 C++: cpp-httplib(헤더 온리, 가장 단순) 또는 Drogon(vcpkg) + MySQL Connector/C++(vcpkg `libmysql` 또는 `mysql-connector-cpp`) + redis-plus-plus(vcpkg). 교재 저장소에 해당 책이 없으므로 공식 문서 중심
  - (b) 혼합: API 서버는 C#(ASP.NET Core)으로 만들고 C++ 게임 서버(3-1)와 연동. 실무에서 흔한 조합이며 정식 인정. 12주 첫 주에 "필수 C# 가이드" 통독 20h 추가
- 어느 경로든 **공통 학습(DB·Redis·API 설계·동시성)은 동일**하며 평가 기준도 같다

### 1.3 선수 조건
- Phase 3 완료, MySQL 8·Redis(Memurai 또는 WSL2) 로컬 기동

### 1.4 이 Phase가 끝나면 할 수 있는 것
- "동시 100회 구매 요청에서 재화가 정확히 한 번만 차감"되는 API를 만들고 테스트로 증명한다
- EXPLAIN으로 풀 스캔을 찾아 인덱스로 고치고 전/후 시간을 제시한다
- 격리 수준별로 어떤 현상(더티 리드·논리피터블 리드·팬텀)이 생기는지 재현한다
- 게임 서버가 왜 DB를 직접 치지 않고 API 서버를 거치는지(또는 거치지 않는 경우는 언제인지) 설명한다

## 3. 학습 항목 상세

### 3.1 공통 (100h)

**HTTP/REST와 게임 API 설계 (12h)**
- 무엇: HTTP 메서드·상태 코드·헤더, JSON, REST vs 커맨드형(POST 통일) 설계, 게임 API 흐름(버전 체크 → 로그인 → 유저 데이터 로드 → 로비 행동 → 로그아웃), 에러 코드 체계(HTTP 상태 + 애플리케이션 코드), API 버전 관리, 요청/응답 DTO
- 왜: 게임 API는 일반 웹 API와 달리 "로그인 후 대량 데이터 로드", "재화 차감" 같은 특유의 패턴이 있다
- 확인: 4-C 명세 20개 엔드포인트, 에러 코드 표

**인증·인가 (10h)**
- 무엇: 비밀번호 해싱(Argon2/bcrypt/PBKDF2 — 절대 SHA256 단독 금지), 토큰(JWT vs 불투명 토큰) 발급·검증·만료·갱신, Redis 세션(토큰 → 유저ID), 중복 로그인 처리(기존 세션 무효화), 서버 간 인증(공유 시크릿 또는 내부 토큰)
- 왜: 계정 탈취·재화 복제의 첫 방어선
- 확인: 만료 토큰·위조 토큰·다른 유저 토큰으로 요청 시 전부 거부되는 테스트

**MySQL 설계와 쿼리 (24h)**
- 무엇: 정규화와 게임에서의 비정규화 판단(인벤토리 행 vs JSON 컬럼), 키 설계(AUTO_INCREMENT vs UUID/ULID), 인덱스(B-tree, 복합 인덱스 순서, 커버링), EXPLAIN 읽기, JOIN, 페이징, 마이그레이션(버전 관리 스크립트), 샤딩 개념(유저ID 기준)
- 왜: 라이브 서비스에서 가장 흔한 장애가 "느린 쿼리"다
- 확인: 100만 건 유저·1,000만 건 인벤토리 삽입 후 5개 핵심 쿼리의 EXPLAIN과 실행 시간 표, 인덱스 추가 전/후

**트랜잭션·동시성 (20h)**
- 무엇: ACID, 격리 수준 4단계와 각 현상, InnoDB 락(레코드·갭·넥스트키), 데드락과 재시도, `SELECT ... FOR UPDATE`, 낙관적 락(버전 컬럼), 이중 지출 방지 패턴(조건부 UPDATE `WHERE gold >= ?`), 멱등성 키(요청ID 저장), Redis 분산 락(SET NX PX)의 한계
- 왜: "동시 100회 구매" 조건이 이 Phase의 핵심 평가다
- 확인: 격리 수준별 현상 재현 스크립트, 데드락 재현·재시도 성공 로그, 동시 100회 구매 테스트

**Redis 활용 (12h)**
- 무엇: 자료구조(String·Hash·List·Set·ZSet)와 게임 용도(세션·프로필 캐시·랭킹·온라인 목록·큐), TTL, 파이프라인, Lua 스크립트 원자성, 영속성(RDB/AOF) 개념, 캐시 무효화 전략, "Redis에 두면 안 되는 것"(재화 원장)
- 왜: 게임 서버의 실시간 데이터 대부분이 Redis에 있다
- 확인: 랭킹 ZSET 상위 100·내 순위 조회, 세션 TTL 갱신, Lua로 원자적 재고 차감

**서버 연동·배치 (8h)**
- 무엇: 게임 서버 → API 서버 내부 API(게임 결과 저장), 내부 API 인증, 실패 시 재시도·중복 방지, 배치 작업(출석 리셋·우편 만료 정리)을 별도 워커 또는 스케줄러로
- 왜: 실시간 서버와 데이터 서버의 경계를 정하는 훈련
- 확인: 3-1 게임 결과가 API 서버 DB에 저장되고 랭킹이 갱신됨

**통합 테스트 (8h)**
- 무엇: 실제 MySQL/Redis를 쓰는 테스트(테스트 전용 스키마·키 prefix, 테스트 전후 정리), 동시성 테스트(Task/스레드 100개 동시 호출), 픽스처
- 왜: 트랜잭션·락은 목(mock)으로 검증할 수 없다
- 확인: 4-1 통합 테스트 30개, 동시성 테스트 3개

**보안·악용 시나리오 (6h)**
- 무엇: 입력 검증, SQL 인젝션(파라미터 바인딩), 레이트 리밋, 재화 복제·중복 수령·토큰 탈취·리플레이 시나리오, 로그에 민감 정보 금지
- 확인: 4-2 리포트

```
다음 API 명세(첨부)를 공격자 관점에서 본다. 재화 복제, 중복 수령, 토큰 탈취, 리플레이, 파라미터 조작, 레이스 컨디션 관점에서 악용 시나리오를 최소 8개 열거해 달라.

```

격리 수준이 REPEATABLE READ일 때와 READ COMMITTED일 때 결과가 달라지는지도 설명해 달라.
```

```
다음 데이터 항목들에 대해 MySQL·Redis·둘 다 중 어디에 두어야 하는지 각각 근거와 함께 판정해 달라: 골드 잔액, 세션 토큰, 랭킹, 우편함, 출석 기록, 온라인 유저 목록, 상점 재고.

| 100만 건 더미 데이터 생성 스크립트 | 스키마·인덱스의 최종 결정(AI 제안은 측정으로 검증) |

### 5.3 AI가 자주 틀리는 지점
- "SELECT 후 잔액 확인 → UPDATE" 두 쿼리로 재화를 차감하는 코드를 제안(레이스). 조건부 UPDATE 또는 FOR UPDATE로
- 비밀번호를 SHA256+salt로 해싱하는 예제. Argon2/bcrypt/PBKDF2 사용
- JWT를 Redis 세션 없이 쓰면서 "로그아웃"을 구현했다고 하는 예제(무효화 불가)
- 인덱스를 모든 컬럼에 제안. 쓰기 비용을 묻는다
- Redis 분산 락을 만능으로 제시. 락 만료·클라이언트 죽음 시나리오를 묻는다

### 6.2 트랙 과제 4-1. 게임 API 서버 (필수, 88h)

기능 요구사항
1. 계정: 가입(ID·비밀번호 규칙 검증, 해싱), 로그인(토큰 발급, Redis 세션 TTL 1시간), 토큰 갱신, 로그아웃, 중복 로그인 시 기존 세션 무효화
2. 버전 체크·공지·헬스 체크(인증 불필요)
3. 유저 데이터 로드: 로그인 후 1회 호출로 기본 정보·재화·인벤토리 요약·미수령 우편 수 반환
4. 인벤토리: 조회(페이징), 아이템 사용(수량 차감, 0이면 삭제)
5. 우편함: 목록, 수령(첨부 재화/아이템 지급, 1회만), 만료(배치)
6. 출석: 일 1회, 자정(KST) 리셋, 보상 지급
7. 상점: 상품 목록, 구매(재화 차감 + 아이템 지급 + 구매 이력, 하나의 트랜잭션), 재고 있는 상품 1종
8. 랭킹: 게임 결과로 점수 갱신(Redis ZSET), 상위 100, 내 순위
9. 내부 API: 게임 서버(3-1)가 게임 결과 저장·랭킹 갱신 호출(서버 간 인증), 게임 서버는 로그인 토큰 검증도 API 서버(또는 Redis 직접)로 수행
10. 배치 워커: 우편 만료 정리, 출석 리셋(스케줄러 또는 별도 콘솔)

비기능 요구사항
- **동일 계정 동시 100회 상점 구매 요청**에서 재화가 정확히 1회분만 차감되고 아이템도 1개만 지급(정합성 테스트)
- 우편 수령·출석 체크를 동시 50회 요청해도 1회만 처리(멱등성 테스트)
- 로그인 API p99 100ms 이하(로컬, 동시 100 요청, 100만 유저 데이터 상태)
- 100만 유저·1,000만 인벤토리 삽입 후 핵심 쿼리 5개 EXPLAIN에 풀 스캔 없음
- 모든 SQL은 파라미터 바인딩(문자열 결합 금지)
- 로그: 요청ID·유저ID·소요 시간·결과 코드

테스트

- 토큰 vs 세션. JWT만 쓰면 로그아웃이 왜 어려운가
- Redis에 재화 잔액을 두면 안 되는 이유. 예외가 있다면
- 게임 서버가 DB를 직접 치지 않고 API 서버를 거치게 한 이유. 직접 치는 게 맞는 경우는
- 멱등성 키를 어디에 저장하고 언제 지우는가
- (C#) DI 수명 Scoped인 DbConnection을 Singleton 서비스에 주입하면 무슨 일이 생기는가
- (C++) 연결 풀을 직접 만들 때 스레드 안전성과 연결 유효성 검사를 어떻게 하는가

## 8. 흔한 막힘 포인트

| 증상 | 원인 | 대처 |
|---|---|---|
| 동시 구매 테스트에서 가끔 2회 차감 | SELECT 후 UPDATE 분리, 트랜잭션 밖에서 잔액 확인 | `UPDATE ... SET gold = gold - ? WHERE id = ? AND gold >= ?` + 영향 행 수 확인 |
| 데드락 에러 간헐 발생 | 두 트랜잭션이 다른 순서로 행 락 | 락 획득 순서 통일(유저 → 아이템), 재시도 |
| Redis 세션이 사라짐 | TTL 갱신 누락, Memurai 재시작 | 요청마다 TTL 연장, 영속성 설정 확인 |
| 100만 건 삽입이 너무 느림 | 행 단위 INSERT | 배치 INSERT(1,000행 단위), 인덱스 삽입 후 생성 |
| EXPLAIN이 인덱스를 안 탐 | 컬럼 순서, 함수 적용, 타입 불일치 | 조건 컬럼을 선두로, `WHERE DATE(col)` 금지, 타입 맞춤 |
| 테스트가 서로 데이터를 오염 | 공용 스키마 | 테스트 전용 스키마 + 각 테스트 전 정리, Redis 키 prefix |
| (C#) `WebApplicationFactory`에서 설정이 안 바뀜 | 환경 이름 | `ASPNETCORE_ENVIRONMENT=Test`, `appsettings.Test.json` |
