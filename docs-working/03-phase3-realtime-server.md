# Phase 3. 실시간 게임 서버 아키텍처 (8~11주, 160h)

> 공통 90h / 트랙 70h. 이 Phase가 끝나면 학습자는 게임 로직이 들어간 실시간 서버를 **스레드 모델부터 설계**하고, 설계 문서와 코드가 일치하는 상태로 완성한다.

## 1. 개요

### 1.1 목표
- 게임 서버 스레드 모델 4가지를 비교하고 상황에 맞게 선택·근거를 문서화한다
- 룸 단위 액터(단일 스레드 로직) 구조로 락 없는 게임 로직을 만든다
- 세션·유저·룸·매칭의 상태 머신을 설계하고 타임아웃·재접속·관전을 처리한다
- 서버 권위(server authority) 판정과 입력 검증을 구현한다
- 네트워크/로직/규칙 계층을 분리해 게임 규칙을 네트워크 없이 단위 테스트한다
- 설계 문서와 ADR을 먼저 쓰고, 구현 후 불일치를 갱신하는 습관을 만든다

### 1.2 선수 조건
- Phase 2 완료(채팅 서버 500접속, 패킷 라이브러리, 테스트 클라이언트)

### 1.3 이 Phase가 끝나면 할 수 있는 것
- "왜 룸을 단일 스레드로 처리하는가, 대안은 무엇인가"를 장단점과 함께 설명한다
- 100개 룸이 동시에 돌아가는 서버를 만들고 턴 처리 지연 p99를 측정한다
- 룸 로직에 숨은 경쟁 조건을 찾아낸다
- 설계 문서만 보고 다른 사람이 서버 구조를 이해할 수 있게 쓴다

## 3. 학습 항목 상세

### 3.1 공통 (90h)

**스레드 모델 (14h)**
- 무엇: (1) 세션당 스레드, (2) I/O 스레드 + 로직 단일 스레드, (3) 워커 풀 + 공유 상태 락, (4) 룸/엔티티 단위 액터(메시지 큐 + 단일 소비자). 각 모델의 처리량·지연·복잡도·확장성·디버깅 난이도
- 왜: 게임 서버 설계의 첫 결정이고, 면접 단골이며, 잘못 고르면 이후 전부 다시 짠다
- 확인: 4모델을 "오목 100룸", "MMO 존 서버", "FPS 매치 서버" 세 케이스에 각각 적용했을 때의 선택과 근거 표

**룸 액터 패턴 (12h)**
- 무엇: 룸마다 Job 큐, 룸 로직은 한 번에 한 스레드만 실행, 룸 간 통신은 메시지, 룸에 대한 외부 접근 금지(패킷 → Job 변환), 스케줄링(룸을 워커에 배정), 타이머 Job
- 왜: 락 없이 게임 로직을 쓸 수 있고 데이터 경쟁이 구조적으로 사라진다
- 확인: 룸 로직에 락이 하나도 없음을 코드 검색으로 증명하고, 룸 밖에서 룸 상태를 직접 읽는 코드가 없음을 리뷰로 확인

**게임 루프·틱·타이머 (8h)**
- 무엇: 틱 기반 vs 이벤트 기반, 고정 틱과 가변 틱, 타이머 정밀도(Windows 기본 15.6ms, `timeBeginPeriod`/고해상도 타이머), 지연 Job, 타임아웃 검사 주기
- 왜: 턴 타임아웃, 하트비트, 재접속 유예 전부 타이머다
- 확인: 1ms·10ms·100ms 타이머의 실제 발화 간격 분포를 측정한 표

**상태 머신 (10h)**
- 무엇: 세션(접속→인증→로비→매칭 대기→룸→게임→결과→로비), 룸(생성→대기→진행→종료→파괴), 매칭 큐(요청→대기→성사/취소). 각 상태에서 허용 패킷과 전이 조건, 불법 전이 처리
- 왜: 상태 머신이 명시되지 않으면 "로비에서 착수 패킷"이 들어올 때 서버가 이상 동작한다
- 확인: 상태 전이표를 문서화하고, 불법 전이 5개를 테스트로 재현

**서버 권위와 검증 (8h)**
- 무엇: 클라이언트는 요청만, 판정은 서버. 착수 유효성(내 턴인가, 빈 칸인가, 규칙 위반인가), 속도 제한(초당 요청 수), 재현 가능한 랜덤(시드), 치트 시나리오(턴 위조, 다른 룸 패킷, 결과 위조)
- 왜: 온라인 게임의 신뢰 모델의 기초
- 확인: 치트 시나리오 5개를 테스트 클라이언트로 시도해 전부 거부됨을 증명

**동기화 개념 (8h)**
- 무엇: 상태 동기화 vs 입력 동기화, 스냅샷·델타, 보간, 클라이언트 예측·되감기(개념), 틱 레이트와 대역폭, AOI(관심 영역) 개념
- 왜: 오목에는 필요 없지만 Phase 6 확장과 면접에 필요하다. 심화 과제 3-3(액션)에서 일부 적용
- 확인: "30Hz 틱, 100명, 위치 16바이트"일 때 대역폭 계산과 줄이는 방법 3가지

**설계 문서와 ADR (10h)**
- 무엇: 설계 문서 구조(목표·제약·구조·스레드 모델·데이터 소유·패킷 목록·리스크), ADR(맥락·결정·대안·결과), 다이어그램(컴포넌트·시퀀스·상태), 구현 후 불일치 갱신
- 왜: 실무에서 코드보다 먼저 검토받는 산출물이고, 캡스톤 평가의 축이다
- 확인: 3-C 문서를 AI "처음 보는 개발자" 역할에게 주고 "이 문서만으로 구조를 설명해 보라"고 해서 설명이 맞는지 본다

**계층 분리와 테스트 (10h)**
- 무엇: 네트워크(세션·패킷) / 로직(룸·유저·매칭) / 규칙(오목 판정) 분리, 규칙은 순수 함수, 로직은 인터페이스로 네트워크를 추상화, 통합 테스트 시나리오(테스트 클라이언트)
- 왜: 규칙 버그를 서버 띄우지 않고 1초 만에 잡기 위해
- 확인: 규칙 테스트 30개가 네트워크 없이 1초 내 실행

**로깅·설정·종료 (10h)**
- 무엇: 구조화 로그(필드: 세션ID·유저ID·룸ID·패킷ID), 로그 레벨 정책, 설정 파일(JSON/TOML)과 환경별 분리, graceful shutdown 순서(신규 접속 차단 → 룸 종료 통지 → 세션 정리 → 스레드 종료)
- 왜: Phase 5 관측과 운영의 기반
- 확인: 종료 신호 후 5초 내 모든 스레드가 정상 종료되고 로그에 순서가 남는다

### 6.3 공통 과제 3-2. 시나리오 테스트 클라이언트 확장 (필수, 16h)

## 8. 흔한 막힘 포인트

| 증상 | 원인 | 대처 |
|---|---|---|
