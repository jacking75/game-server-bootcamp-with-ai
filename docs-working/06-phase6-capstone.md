# Phase 6. 캡스톤 프로젝트 & 취업 준비 (21~26주, 240h)

> 공통 130h / 트랙 110h. 이 Phase가 끝나면 학습자는 지금까지 만든 것을 **다중 서버 구성의 완성된 서비스**로 통합하고, 남에게 설명 가능한 포트폴리오와 면접 역량을 갖춘다.

## 0. 이 문서 사용법

Phase 1~5와 같은 구조다. §2 일자 블록(101~130일차)을 따라가고, 실습(`L6-C-xx`)은 §3, 과제 상세는 §7에서 찾는다.

이 Phase의 4대 원칙

1. **범위는 ADR로만 바꾼다.** 캡스톤이 실패하는 1번 이유는 범위 팽창이다. 21주 화요일에 범위를 고정하고, 이후 변경은 반드시 ADR로 남긴다.
2. **배포는 하지 않는다.** 서버 4종(API·매칭·게임 2대·배치 워커)을 **로컬 PC에서 포트를 구분해 별도 프로세스로 동시 실행**한다. Windows 서비스 등록·원격 배포·CI/CD는 이 과정 범위 밖이다. 대신 **한 번에 기동/종료하는 PowerShell 스크립트**를 만든다.
3. **문서는 마지막에 몰아 쓰지 않는다.** 24주부터 매일 1시간을 문서에 쓴다. ADR은 결정 즉시 쓴다.
4. **AI가 만든 코드도 전부 설명할 수 있어야 한다.** 면접에서 반드시 나온다. `AI-USAGE.md`가 그 답이다.

| 표기 | 뜻 |
|---|---|
| `L6-C-xx` | 캡스톤 실습(트랙 공통) |
| 🔴 필수 · 🟡 여유 시 | 우선순위 |

## 1. 개요

### 1.1 목표

1. **다중 서버 구성**: API 서버 + 매칭 서버 + 게임 서버 2대 이상 + 배치 워커를 로컬에서 동시 실행하고, 서버 간 통신·상태 공유를 구현한다
2. **세션 라우팅**: 로그인 토큰 → 매칭 → **1회용 접속 티켓** → 게임 서버 접속 흐름을 만든다
3. **서버 다운 처리**: 게임 서버 1대를 강제 종료해도 매칭이 15초 내 그 서버를 제외하고, 유저가 로비 복귀 후 재매칭에 성공한다
4. **품질 증명**: 1,000 동시 접속·200룸·10분을 통과하고 p99를 기록한다
5. **문서화**: README·ARCHITECTURE·ADR 5개·성능 리포트·런북·AI 활용 기록을 갖춘다
6. **취업 준비**: 30분 발표, 60분 모의 면접 3회, 이력서, 기술 블로그 3편

### 1.2 선수 조건 자가 진단 (30분)

| # | 질문 | 통과 기준 |
|---|---|---|
| 1 | 3-1 게임 서버가 100룸 부하를 통과했는가 | `LOAD-3-1.md` 보유 |
| 2 | 4-1 API 서버가 동시성 테스트를 통과했는가 | 테스트 로그 보유 |
| 3 | 5-C 관측 스택이 동작하는가 | 대시보드·알람 |
| 4 | 5-4 복원력 패턴(재시도·서킷·백프레셔)이 구현되어 있는가 | 코드·테스트 |
| 5 | 게임 서버를 다른 포트로 2개 동시 실행할 수 있는가 | 실행 확인 |
| 6 | 공용 라이브러리(PacketLib·Rules·Pool)가 참조 가능한가 | 빌드 확인 |

**4개 미만이면 캡스톤 범위를 줄인다**(게임 서버 2대 → 1대 + 매칭 서버 분리만, 또는 콘텐츠 확장 제외). 미완 과제를 끌고 가면 6주 안에 끝나지 않는다.

### 1.3 이 Phase가 끝나면 할 수 있는 것

- 채용 면접에서 **아키텍처 다이어그램 하나로** 자기 서버 전체를 설명한다
- "AI가 만든 부분과 내가 만든 부분"을 구분하되 **AI가 만든 부분도 전부 설명**한다
- 처음 보는 사람이 README만 보고 10분 내 로컬 실행에 성공한다
- 매칭 서버 핵심(대기열·서버 선택·티켓)을 120분 안에 재구현한다
- 1,000접속 부하 결과와 서버 다운 복구 시간을 수치로 제시한다

## 3. 실습 카탈로그

### 3.1 캡스톤 실습 (L6-C)

#### L6-C-01 범위 표 작성 (60분) 🔴
- **단계**: 기능을 행으로, `필수/선택/제외 · 예상 시간 · 근거` 를 열로. 예상 시간의 합이 가용 시간의 70%를 넘으면 무언가를 제외한다
- **확인 기준**: 제외 항목마다 "왜 빼도 포트폴리오 가치가 유지되는가"가 적혀 있다

#### L6-C-02 AI PM 리뷰 (60분) 🔴
- **단계**: §6.1 프롬프트로 일정 위험 3개·제외 후보·필수 항목을 받고, 각각 수용/반박을 기록
- **확인 기준**: 최종 결정이 **내 판단**으로 기록되고 ADR-0010에 반영

#### L6-C-03 서버 간 통신 비교 (60분) 🔴
- **단계**: Redis Pub/Sub / gRPC / 자체 TCP를 지연·신뢰성·구현 비용·디버깅 난이도·유실 특성으로 비교
- **확인 기준**: 표 + 선택 근거. Pub/Sub 선택 시 **메시지 유실 특성**을 ADR에 명시

#### L6-C-04 하트비트 설계 (45분) 🔴
- **단계**: 키 구조(`server:{id}`), 필드(접속 수·룸 수·버전·메트릭 포트), 주기 5초·TTL 15초, 갱신 실패 처리
- **확인 기준**: TTL ≥ 주기 × 3 근거 계산

#### L6-C-05 공용 라이브러리 정리 (90분) 🔴
- **단계**: `Shared/`로 PacketLib·Rules·Pool·Resilience 이동, 순환 참조 제거, 버전 태그
- **확인 기준**: 네 서버가 모두 `Shared/`를 참조해 빌드됨

#### L6-C-06 실행 스크립트 (75분) 🔴

무엇이 먼저 병목이 되고 무엇을 바꿔야 하는가를 순서대로 3개 짚어 달라.
각각에 대해 내가 먼저 답해 보겠다: "(내 답)". 내 답의 빈틈만 지적해 달라.
```

**이력서 리뷰**
```

채용 담당자와 기술 면접관 두 관점에서 각각

**구성 요구사항**

1. **서버 구성**: API 서버(4-1 확장) 1대 + 매칭 서버 1대 + 게임 서버 2대 이상(같은 바이너리, 다른 포트/ID) + 배치 워커 1개. **모두 로컬 PC에서 별도 프로세스로 동시 실행**(Windows 서비스 등록 없음)
2. **흐름**: 클라이언트 → API 로그인(토큰) → 매칭 서버 접속(토큰 검증) → 매칭 요청 → 게임 서버 선택·**티켓 발급**·주소 통지 → 게임 서버 접속(티켓 검증) → 플레이 → 결과 → 게임 서버가 API에 저장(재시도 큐) → 랭킹 갱신 → 로비 복귀·재매칭

### 8.2 재구현 시험 (AI 없음, 120분)

**문제**: 매칭 서버 핵심을 구현하고 제공 테스트 4개를 통과시킨다(네트워크는 페이크, Redis는 인메모리 대체 가능).

요구 기능
```
Matcher.Request(userId)            // 대기열 등록
Matcher.Cancel(userId)
Matcher.Tick(nowMs)                // 매칭 주기: 2인 성사 시 서버 선택 + 티켓 발급 + 배정 통지
ServerRegistry.Heartbeat(serverId, rooms, version, nowMs)
TicketStore.Issue(userId, roomId, serverId) / Consume(ticket)   // 1회용
```
제공 테스트
1. **2인 성사**: 두 명이 요청하면 같은 룸에 배정되고 서로 다른 티켓을 받는다
2. **서버 제외**: 하트비트가 15초 이상 끊긴 서버는 후보에서 제외된다
3. **취소**: 취소한 유저는 성사되지 않는다(취소 직후 다른 유저가 와도 대기)
4. **티켓 1회용**: 같은 티켓을 두 번 소비하면 두 번째는 실패한다

**통과 기준**: 120분 내 4개 통과.

### 8.3 최종 발표·면접

- **30분 발표**: 5점 척도 평균 4.0 이상. 다이어그램 1장으로 전체 구성을 설명하고, 핵심 결정 3개를 근거와 함께 방어
- **60분 모의 면접** 마지막 회차 평균 4.0 이상

### 8.4 최종 설명 시험 질문 은행

1. 전체 구성을 다이어그램 하나로 그리고 로그인부터 결과 저장까지 데이터 흐름을 설명하라
2. 게임 서버를 10대로 늘리면 무엇을 바꿔야 하는가. 매칭 서버가 병목이 되면
3. 티켓을 Redis에 두는 이유. 티켓 없이 토큰만으로 하면 어떤 문제가 있는가
4. 티켓 재사용을 어떻게 막았는가(원자성 보장 방법)
5. 게임 서버가 죽었을 때 진행 중 게임을 어떻게 처리했고, 다른 선택지는 무엇이었는가
6. 죽은 서버의 유저에게 서버가 통지할 수 없다는 제약이 설계에 어떤 영향을 줬는가
7. 결과 저장 재시도 큐가 프로세스 종료로 사라지면 어떻게 되는가. 허용했다면 근거는
8. 하트비트 주기 5초·TTL 15초를 어떻게 정했는가
9. 매칭 서버가 죽으면 무엇이 멈추고 무엇이 계속되는가
10. 상태 배치표에서 "잃어도 되는 것"과 "잃으면 안 되는 것"의 기준은
11. 1,000접속에서 병목은 무엇이었고 어떻게 개선했는가. 기각한 가설은
12. p99 수치가 어디서 나왔고 어떻게 재현하는가
13. 대시보드에서 장애를 어떤 순서로 진단하는가

## 9. 흔한 막힘 포인트

| 증상 | 원인 | 대처 |
|---|---|---|
| 범위가 계속 커진다 | ADR 없이 기능 추가 | 범위 변경은 ADR로만, 주간 리뷰에서 "제외" 결정 |
| 매칭 서버가 죽은 게임 서버로 배정 | 하트비트 TTL·검사 주기 불일치, TOCTOU | TTL > 주기 × 3, **배정 직전 재확인** |
| 티켓이 재사용된다 | 검증 후 삭제가 원자적이지 않음 | Redis `GETDEL` 또는 Lua로 검증+삭제를 한 번에 |
| 룸이 한 서버에 몰린다 | 룸 수 갱신 지연, 동시 배정 | 하트비트 주기 단축 또는 배정 시 카운터 즉시 증가 |
| 결과 저장이 중복된다 | 재시도 큐 + 멱등성 미적용 | gameId를 멱등성 키로, API 측 중복 검사 |
| 서버 다운 후 유저가 멈춰 있다 | 클라이언트 끊김 감지 없음 | 클라이언트 타임아웃 + 로비 복귀 로직(테스트 클라이언트에도 구현) |
| 로컬에서 4종 프로세스가 포트 충돌 | 포트 하드코딩 | 전부 인자/환경 변수로, 스크립트에서 주입 |
| 종료 후 프로세스가 남는다 | 자식 프로세스 추적 안 함 | `stop-all.ps1`에서 PID 파일 또는 프로세스 이름+포트로 정리 |
| traceId가 서버 간에 안 이어짐 | 전파 누락 | 패킷·HTTP 헤더에 traceId 필드 추가, 로그 필드 표준 |
| 문서 쓸 시간이 없다 | 마지막에 몰아 씀 | 24주부터 매일 1시간, ADR은 결정 즉시 |
| 모의 면접에서 자기 코드를 설명 못 함 | AI 생성 코드 미검토 | 해당 부분을 AI 없이 재구현하고 `AI-USAGE.md`에 기록 |
| 데모 영상이 10분을 넘는다 | 대본 없이 촬영 | 4구간 대본 작성 후 촬영, 실패 구간만 재촬영 |
| 부하 테스트에서 클라이언트가 병목 | 단일 프로세스 | 2개 프로세스로 유저 ID 범위 분리 |

## 10. 과정을 마친 뒤

### 10.1 취업 후 학습 목록 (이 과정에서 의도적으로 제외한 것)

| 주제 | 왜 제외했나 | 언제 배우면 되나 |

| 배포·CI/CD | 학습 시간을 서버 구현·운영 품질에 집중하기 위해 | 입사 후 팀의 파이프라인을 따라가며 |

| 로드밸런서·클라우드·멀티리전 | 서버 2대 규모를 넘는 인프라 | 로드맵 교재 Ch.8 → 실무 |
| UDP 기반 동기화·지연 보상 | 오목/턴제에는 불필요 | FPS·액션 장르로 갈 때 |

### 10.2 계속할 것

- **캡스톤을 계속 개선한다.** 채용 과제·면접에서 받은 질문을 이슈로 등록하고 하나씩 해결한다
- **블로그를 이어 쓴다.** 개선 하나당 글 하나가 곧 포트폴리오다
- **면접 기록을 남긴다.** 받은 질문·답변·부족했던 점을 정리해 다음 지원에 반영한다
- **이 커리큘럼에서 틀렸거나 부족했던 부분**을 과정 저장소 이슈로 남긴다(다음 학습자를 위해)
