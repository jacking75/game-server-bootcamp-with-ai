# Phase 6. 캡스톤 프로젝트 & 취업 준비 (21~26주, 240h)

> 공통 130h / 트랙 110h. 이 Phase가 끝나면 학습자는 지금까지 만든 것을 **다중 서버 구성의 완성된 서비스**로 통합하고, 남에게 설명 가능한 포트폴리오와 면접 역량을 갖춘다.

## 1. 개요

### 1.1 목표
- 로그인/API 서버 + 매칭 서버 + 게임 서버 2대 이상으로 구성된 서비스를 만들고 배포한다
- 게임 서버 수평 확장, 세션 라우팅, 서버 상태 공유, 서버 다운 시 처리를 설계·구현한다
- 1,000 접속·200룸 부하와 서버 1대 강제 종료 시나리오를 통과한다
- README·아키텍처 문서·ADR·성능 리포트·데모 영상을 갖춘 포트폴리오를 완성한다
- 30분 발표와 60분 모의 면접을 통과한다

### 1.2 선수 조건
- Phase 5 완료(배포 환경·관측·더미 클라이언트·런북)

### 1.3 이 Phase가 끝나면 할 수 있는 것
- 신입 게임 서버 개발자 채용 과제·기술 면접에서 자기 서버를 아키텍처 다이어그램 하나로 설명한다
- "AI가 만든 부분과 내가 만든 부분"을 구분하되 AI가 만든 부분도 전부 설명한다
- 처음 보는 사람이 README만 보고 10분 내 로컬 실행에 성공하게 한다

### 2.1 21주 월~화: 범위 결정 절차
1. 06 문서 §6.1 요구사항을 읽고 "필수/선택/제외" 표를 직접 작성한다
2. AI를 PM/아키텍트 리뷰어로 세워 "4주 안에 되는가"를 검토받는다(§5.1 프롬프트)
3. 결정을 ADR-0010(범위)과 주차별 마일스톤 표로 고정한다. 이후 범위 변경은 ADR로만
4. 공용 라이브러리(2-2 패킷, 규칙, 클라이언트 툴)를 별도 프로젝트로 정리하고 버전 태그를 단다

## 3. 학습 항목 상세

### 3.1 공통 (130h)

**다중 서버 구성 (16h)**
- 무엇: 서버 종류별 역할(로그인/API, 매칭, 게임, 배치), 서버 목록 관리(정적 설정 vs Redis 등록), 하트비트로 서버 상태(접속 수·룸 수·버전) 공유, 서버 간 통신 선택(Redis Pub/Sub, gRPC, 자체 TCP)과 근거, 내부 API 인증
- 확인: ADR "서버 간 통신 방식", 서버 목록이 Redis에서 30초 내 갱신됨을 확인

**매칭 서버 (16h)**
- 무엇: 매칭 서버 분리 이유, 대기열 자료구조, 매칭 주기, 성사 시 게임 서버 선택(룸 수 최소·버전 일치·정상 하트비트), 배정 통지(게임 서버 주소 + 1회용 접속 티켓), 티켓 검증(게임 서버가 Redis에서 확인), 취소·타임아웃, 매칭 서버 자체 장애 시 대기열 복구
- 확인: 게임 서버 2대에 룸이 고르게 분배되는 로그, 위조 티켓 거부 테스트

**세션 라우팅과 상태 저장 위치 (12h)**
- 무엇: 유저가 어느 게임 서버에 있는지(Redis), 로그인 토큰·게임 세션·룸 상태 각각의 저장 위치와 근거, 게임 서버 재시작 시 잃어도 되는 것/안 되는 것, 스케일 아웃 시 "상태 없는 서버"와 "상태 있는 서버"의 차이
- 확인: 상태 배치표(데이터 × 저장 위치 × 손실 허용 여부)

**서버 다운 처리 (14h)**
- 무엇: 게임 서버 하트비트 끊김 감지(매칭 서버·Redis TTL), 해당 서버 룸 유저 처리(클라이언트에 종료 통지는 불가 → 클라이언트 측 끊김 감지 + 로비 복귀), 진행 중 게임 결과(무효 처리 vs 저장), 재매칭 계속 진행, 결과 저장 실패 시 로컬 큐 보관·재시도
- 확인: 게임 서버 1대 강제 종료 시나리오 통과

**문서화 (20h)**
- 무엇: README(한 화면 요약·구성도·10분 실행 절차·테스트 실행·배포), 아키텍처 문서(컴포넌트·시퀀스·상태·배포 다이어그램), ADR 5개 이상, 프로토콜·API 명세 최종본, 성능 리포트, 런북, "AI 활용 기록"(어디에 AI를 썼고 어떻게 검증했는가)
- 확인: AI "처음 보는 개발자" 역할이 README만으로 실행 절차를 재현

**발표·면접 (32h)**
- 무엇: 30분 발표 구성(문제 → 설계 → 핵심 결정 3개 → 수치 → 장애 대응 → 회고), 다이어그램 1장으로 전체 설명 연습, 기술 면접 빈출(네트워크·OS·DB·동시성·언어), 포트폴리오 심층 질문 대비, 코딩 테스트 기초(배열·해시·정렬·BFS/DFS·이분 탐색·우선순위 큐), 이력서 서술법(문제 → 선택 → 결과 수치)
- 확인: 모의 면접 3회 기록과 회차별 개선점

**포트폴리오 정리 (20h)**
- 무엇: Phase 2~5 저장소 README 표준화, 테스트·CI 정비, 포트폴리오 인덱스(GitHub Profile README 또는 정적 페이지), 기술 블로그 3편
- 확인: 인덱스에서 각 저장소로 이동해 CI 배지 녹색, README 실행 절차 존재

## 6. 과제 명세

### 6.1 캡스톤 6-1. 실시간 멀티플레이 게임 서버 스택 (필수, 160h)

구성 요구사항
1. 서버 구성: API 서버(4-1 확장) 1대, 매칭 서버 1대, 게임 서버 2대 이상(같은 바이너리, 다른 포트/ID), 배치 워커 1개. 모두 배포 머신에서 Windows 서비스로 실행
2. 흐름: 클라이언트 → API 로그인(토큰) → 매칭 서버 접속(토큰 검증) → 매칭 요청 → 게임 서버 선택·티켓 발급·주소 통지 → 게임 서버 접속(티켓 검증) → 플레이 → 결과 → 게임 서버가 API에 저장(재시도 큐) → 랭킹 갱신 → 로비 복귀·재매칭
3. 서버 상태: 게임 서버는 5초마다 Redis에 하트비트(접속 수·룸 수·버전, TTL 15초). 매칭 서버는 하트비트 유효한 서버 중 룸 수 최소를 선택
4. 서버 다운: 게임 서버 1대 강제 종료 시 매칭 서버가 15초 내 제외, 해당 서버 유저는 클라이언트 측 끊김 감지 후 로비 복귀 → 재매칭 성공, 진행 중이던 게임은 "무효" 처리 기록
5. 게임 콘텐츠(택1): (a) 오목 + 관전 + 룸 채팅 + 시즌 랭킹 + 전적, (b) 2D 액션 4인(3-3b 확장), (c) 새 간단 게임(사전 승인)
6. 관측: Phase 5 대시보드에 매칭 서버·게임 서버별 패널 추가, 알람 3개 이상
7. 배포: CI/CD로 서버 4종 배포, 게임 서버는 1대씩 순차 배포(무중단은 선택)

품질 요구사항
- **1,000 동시 접속·200룸 이상**(5-1 "full" 시나리오, 램프업 20명/초) 10분 통과, 착수 p99·매칭 성사 시간 p99·로그인 p99 기록
- 게임 서버 1대 강제 종료 시나리오 통과(위 4번), 복구 시간 기록
- 단위·통합 테스트 CI 통과(규칙·로직·API·매칭 서버 대기열)
- 런북 갱신(매칭 서버 다운·게임 서버 다운·Redis 다운)

문서 요구사항
- README: 한 화면 요약, 구성도, 10분 내 로컬 실행 절차, 테스트·배포 방법
- `ARCHITECTURE.md`: 컴포넌트·시퀀스(로그인~플레이~결과)·상태·배포 다이어그램, 상태 배치표
- ADR 5개 이상(서버 간 통신, 매칭 방식, 티켓 설계, 상태 저장 위치, 서버 다운 정책 + 범위 ADR)
- `PROTOCOL.md`·`API.md` 최종본, `PERF-REPORT.md`(캡스톤 기준), `RUNBOOK.md`, `AI-USAGE.md`
- 데모 영상 5분(구성 설명 1분, 플레이 2분, 서버 다운·복구 1분, 대시보드 1분)

제출물: 저장소, 배포 접속 정보, 영상
